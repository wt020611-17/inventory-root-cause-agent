# 技术架构与接口

> 本文件把 [[../项目完整方案]] 中的总体技术路线落成开发契约。业务口径以 [[01_业务口径与需求]] 为准，验收以 [[03_验收标准]] 为准。

## 1. 设计目标与约束

- 数值、阈值命中和根因得分由确定性代码产生，LLM 不得生成或改写。
- Agent 负责意图理解、参数组织、工具编排和回答组织。
- 每个结论必须追溯到指标、规则或关系路径。
- 无 LLM 密钥时，结构化分析链路仍可运行。
- 领域结果统一使用 `ok`、`empty`、`blocked`、`error`；请求校验失败使用 API 错误码 `invalid_request`，不伪装成领域执行结果。
- 仅使用纯合成数据，不接入公司代码、真实表名、客户数据、凭据或内部地址。

## 2. 总体架构与数据流

```text
Streamlit / API Client
          |
       FastAPI
          |
  Agent Workflow / Structured Analysis
     |          |           |
 Inventory   Metrics   Graph + Root Cause
     |                      |
 SQLite                 NetworkX
          |
  Logging / Trace / Evaluation
```

核心分析链路：

```text
解析请求
  -> 校验参数
  -> 查询库存
  -> 计算确定性指标
  -> 按需追踪业务关系
  -> 执行确定性根因评分
  -> 校验证据完整性
  -> 组织结构化结果或自然语言回答
```

## 3. 模块职责与边界

| 模块 | 职责 | 输入 | 输出 | 不负责什么 |
|---|---|---|---|---|
| `app/domain` | 实体、值对象、枚举和领域结果 | 已校验领域字段 | 领域模型 | 数据库和 Web 框架逻辑 |
| `app/repositories` | 数据访问接口与实现 | 查询条件 | 领域实体/查询结果 | 业务归因判断 |
| `app/services` | 指标计算、关系分析、根因规则等确定性用例 | 领域对象与配置 | 可测试的结构化结果 | 自然语言生成 |
| `app/tools` | 将服务封装成强类型 Agent 工具 | Pydantic 输入 | Pydantic 输出 | 重复实现业务算法 |
| `app/agent` | 状态、节点、路由、校验和降级 | 用户问题/结构化请求 | 分析状态与回答 | 改写计算值和根因得分 |
| `app/api` | HTTP 传输、鉴权边界、请求响应映射 | HTTP 请求 | 统一 API 响应 | 在路由中实现业务规则 |
| `evals` | Agent 样例、评分和基线结果 | 固定评测集 | 可复现报告 | 替代工程测试 |

## 4. 数据与存储边界

- 领域实体及字段以 [[02_数据准备清单]] 为准。
- MVP 只持久化 Material、Warehouse、InventoryMovement、PurchaseOrder、ProductionOrder 五类实体。
- 当前库存由流水聚合，不建快照表；图边由业务外键派生，不建通用关系表。
- 第一版关系图使用 NetworkX 本地适配器；业务层不依赖具体图库。
- 第一版结构化持久化使用 SQLite + SQLAlchemy；Repository 接口隔离具体实现。
- 合成数据生成必须支持固定随机种子，确保测试与评测可复现。

## 5. Agent Tool 契约

| Tool | 核心输入 | 核心输出 | 责任边界 |
|---|---|---|---|
| `list_inventory_risks` | 仓库、物料类别、分析日期 | 风险物料清单、关键指标和数据状态 | 面向风险清单用例 |
| `analyze_material_root_cause` | 物料、仓库、分析日期 | 指标、三类候选根因和证据 | 编排确定性服务，不让 LLM 评分 |
| `trace_evidence` | 物料、仓库、证据类型、最大跳数 | 采购单/生产单节点、关系和路径 | 面向证据核对并限制结果规模 |

指标计算和单条根因规则保留在 `app/services` 内部，不把每个 Python 函数都注册成 Tool。所有 Tool 输入输出使用严格 Pydantic 模型，并拒绝未知字段。

## 6. API 契约

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/health` | 健康检查 |
| POST | `/api/v1/chat` | 自然语言分析入口 |
| POST | `/api/v1/analysis` | 结构化分析入口 |

统一响应骨架：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "..."
}
```

进入编码前还需在实现任务中冻结：各接口请求模型、响应模型、业务错误码和 HTTP 状态码映射。

## 7. 状态、失败与降级

| 状态 | 含义 | 行为 |
|---|---|---|
| `ok` | 执行成功且有结果 | 返回数据和证据 |
| `empty` | 执行成功但无匹配数据 | 返回空结果说明，不伪造结论 |
| `blocked` | 有事实但质量或证据问题阻止结论 | 保留事实并请求核验 |
| `error` | 依赖或内部执行失败 | 返回稳定错误结构和 Trace ID |

参数缺失、冲突或格式错误由 API/Agent 校验层返回 `invalid_request`；此时 Tool 和领域服务尚未执行，因此不进入 `ResultStatus`。

- LLM 不可用：返回结构化指标和规则归因结果。
- 图关系为空：保留结构化分析，并标记关系证据不足。
- Tool 短暂失败：只对可重试错误做有限次数重试。
- 证据校验失败：不输出确定性结论，保留执行摘要供排查。
- 参数缺失：保留当前会话已确认的物料、仓库和分析日期，只追问必要字段；MVP 使用可替换的内存会话存储。

## 8. 日志、追踪与安全

- 每次请求生成 Trace ID，贯穿 API、Agent、Tool 和服务日志。
- 日志只记录节点、工具、耗时、结果状态和错误摘要，不暴露模型私有推理。
- 密钥只从环境变量读取，仓库仅提交 `.env.example`。
- 对物料 ID、日期范围、图跳数和返回规模设置显式限制。
- Prompt 使用版本号管理，并在 Trace 中记录版本，不记录完整私有提示词。

## 9. 测试与评测

- 单元测试：指标公式、根因规则、边界、空值和非法输入。
- 集成测试：Repository、图适配器、Tool 契约和 API。
- 端到端测试：从请求到带证据回答的完整链路及降级链路。
- Agent 评测：工具选择、参数抽取、任务完成、证据引用和拒答/降级。
- 所有简历指标必须记录评测集、命令、结果文件和对应 Commit。

## 10. Phase 0 技术决策

- [x] 使用 Python 3.11.9；依赖版本锁文件在 Phase 0 收尾时从已验证环境生成。
- [x] 使用 LangGraph 实现小型固定工作流，不实现开放式长链 ReAct。
- [x] 领域状态固定为 `ok`、`empty`、`blocked`、`error`；API 参数错误使用 `invalid_request`。
- [x] Tool 固定为三个用例级入口；完整 Pydantic 字段在 Phase 1/2 随测试实现，不新增 Tool。
- [x] Trace 最少记录 `trace_id`、节点/Tool 名、耗时、状态、错误类别、模型和 Prompt 版本；不记录密钥、完整提示词或私有推理。
- [x] 会话上下文只保存已确认的物料、仓库、分析日期和意图，使用可替换内存存储，TTL 30 分钟、最多 4 轮；Redis 属于扩展适配器。
